# 文字 CLUT 全链路与"屏蔽式 CLUT"代码注入方案

> 状态: 全链路已破解并 savestate 实证；v17 镜像已构建，**实机验证排查中**

## 0. 一句话结论

文字颜色**不来自任何静态调色板数据**，而来自一个**每帧被重写的 RAM 工作区**，
经一个**唯一的上传函数**送入 VRAM。因此"改数据"永远无效，
唯一正确的做法是**在该上传函数内注入代码**，在上传前把工作区改写成
"屏蔽式 CLUT"（每个窗口只放行对应套的 bit），从而消除 4 套字形的叠影。

---

## 1. 问题回顾

v15/v16e 采用"4 套字形打包进同一 12×12 槽（各占 4bpp 的一个 bit）+
CLUT 分页决定可见套"的思路。实现方式是**改写 CLUT 段数据**（`rewrite_clut`）。
实测结果：

- 对话文字**多层叠影**（4 套笔画同时可见）；
- 场景图形调色板被破坏（`rewrite_clut` 改错了对象）。

## 2. 全链路破解（关键地址）

### 2.1 `0x3C00` = CLUT 字段（不是 TPAGE）

- CLUT 构造函数 `0x80165ED0`：`v0 = (Y << 6) | ((X >> 4) & 0x3F)`
- 文字行渲染调用点 `0x80145DA8`：硬编码 `Y = 240`
- 窗口号来源 `0x80145D9C`：`andi $s0, $s0, 0x000F`（窗口 = 属性低 4 位）
- => 文字 CLUT = `0x3C00 | win`（CY=240，CX=win×16）

RAM 命令缓冲实测分布：`0x3C00`×22（行 240 win0，主文字）、
`0x3C49`×9 / `0x3C48`×3（行 241 win9/win8）。

### 2.2 上传函数 `0x8013769C`（文字链路唯一收口）

```
lbu  $v0, [0x8010EBF6]        ; 全局上传标志
beq  $v0, $zero, exit         ; 标志=0 → 直接返回
andi $v0, $v0, 0x0080
bne  $v0, $zero, second       ; bit7=1 → 只传第二份
first:  LoadImage(rect(0,240,256,16), src=RAM 0x80032000)   ; 文字调色板
second: LoadImage(rect(0,496,256,16), src=RAM 0x80034000)
sb   $zero, [0x8010EBF6]      ; 清标志
```

调用者（主循环）：`0x801314FC`、`0x80131D18`。

### 2.3 数据链

```
INIT.EMI seg1 (文件偏移 0x8800, 512B, sig=0x8002E000)
INIT.EMI seg3 (文件偏移 0x11000, 512B, sig=0x8002E200)
        │ 加载
        ▼
RAM 0x8002E000 / 0x8002E200        ← "源区"
        │ 复制函数（按行/全量/批量）
        │   0x8013772C（全量 16 行）、0x801377F8（按行）、0x8013A784（批量窗口）
        ▼
RAM 0x80032000（工作区，8KB = 16 行 × 512B = 16 行 × 16 窗 × 16 色）
        │ 上传（标志触发）
        ▼
VRAM (0,240,256,16) = 行 240-255  ← 文字调色板
```

`INIT.EMI` 段表（实测）：`seg1 @0x8800`、`seg3 @0x11000`，
其中 `sig` 即该段的 RAM 加载地址。

### 2.4 行/窗口归属（实测结论）

| 工作区 | 对应 VRAM | 用途 |
|--------|-----------|------|
| 行 0 | 行 240 | **文字**（主） |
| 行 1 | 行 241 | 文字（`0x3C48/0x3C49`） |
| 行 2-15 | 行 242-255 | **背景/图形** |

=> **只改工作区行 0/行 1 完全不影响背景。**

### 2.5 为什么"改 VRAM 现值永远无效"

每帧顺序：**上传调色板 → 绘制文字 → 帧缓冲绘制又覆盖 VRAM 行 240**。
savestate 捕获到的行 240 是帧末的"污染态"（其内容在 RAM 全库 0 命中）。
因此对 savestate 里 VRAM 行 240 的任何修改都会被下一帧覆盖。

---

## 3. 为什么"改数据"路线失败

- 源区 `0x8002E000` / `INIT.EMI` 的 CLUT 数据 = **背景与文字共享池**
  （实测：改它会同时把背景调色板变白）；
- 而文字调色板的"真实现值"是运行时工作区，静态数据改了也会被复制/上传流程回填；
- 结论：**CLUT 必须在"上传函数内"改写**（运行时代码层），而不是在镜像数据层。

## 4. 代码注入方案

### 4.1 注入点

| 项 | 值 |
|----|-----|
| 注入地址 | `0x801376DC`（原 `addiu $v0,$zero,16`） |
| 替换为 | `jal 0x801BB23C` |
| 延迟槽 | `0x801376E0`（`sh $zero,16($sp)`）保持不变 |
| 新函数位置 | `0x801BB23C`（EXE 空闲区，4 字节对齐） |
| 新函数规模 | 247 条指令（988 B） |

新函数刻意**先执行原指令** `addiu $v0,$zero,16`（上传 jal 的延迟槽
`sh $v0,22($sp)` 需要 `$v0` = 16）。

### 4.2 屏蔽式 CLUT（每窗只放行对应套 bit）

| 套 | bit | 放行窗口 |
|----|-----|----------|
| 0 | bit0 | win 0, 4, 5, 6, 7, 8, A, D |
| 1 | bit1 | win 1, 9 |
| 2 | bit2 | win 2, B |
| 3 | bit3 | win 3, C |
| — | — | win E/F 不动 |

每个窗口 16 色：`索引 j` = `0x7FFF`（白）若 `(j >> bit) & 1`，否则 `0x0000`（透明）。

生成规则（示例 win0/bit0）：
```
word[8] = 7FFF0000 ×8      ; 偶索引透明、奇索引白
```
（`word` = 相邻两索引打包，低半字 = 偶索引，高半字 = 奇索引）

### 4.3 寄存器保护

新函数仅使用 `$v0`（补原指令）、`$t0/$t1/$t3`（临时），
不触碰 `$a0/$a1`（LoadImage 参数）、`$sp`、`$ra`。

### 4.4 为什么这样就"永远有效"

注入点位于上传函数内部，**每次上传都会自动重新改写工作区**
（清除标志、复制函数回填都无法绕过），无需任何额外维护。
