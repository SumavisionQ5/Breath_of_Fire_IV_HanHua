## 2. 硬编码 LBA 文件表（重要）

游戏**不解析 ISO9660 目录**，而是使用一张硬编码的文件表：

| 项目 | 值 |
|------|-----|
| RAM 地址 | `0x8016BCE4` |
| 文件偏移 | `0x07ACE4` |
| 项数 | **516** |
| 起始 LBA | 95002（`PLAYER/PL012.EMI`） |
| 结束 LBA | 278462 |
| 覆盖范围 | PLAYER / SCENARIO / SYSTEM / WORLD |

其中 **`SYSTEM/INIT.EMI` 的索引为 82**（LBA 98960）。

表结构：连续的 `u32` LBA 值，按文件顺序排列。

> **对汉化的意义**：所有文件的物理位置在 EXE 中硬编码。若通过 ISO 目录搬移文件
> （如 `move_file_in_iso.py`），**EXE 中的这张表不会同步更新**，游戏会读取旧位置！
> 这是 v3 版本"游戏能启动但文本异常"的重要嫌疑点之一。

## 3. EMI 容器解析逻辑

### 3.1 校验代码

定位到 EMI 格式校验代码位于 RAM `0x80133058` ~ `0x8013315C`：

```asm
0x80133074: lui   $v0, 0x8013
0x80133078: addiu $t4, $v0, 0x800      ; t4 = 0x80130800 ("MATH_TBL" 字符串)
0x8013307C: lwl   $t1, 3($t4)
0x80133080: lwr   $t1, ($t4)           ; 载入 "MATH"
0x80133084: lwl   $t2, 7($t4)
0x80133088: lwr   $t2, 4($t4)          ; 载入 "_TBL"
0x8013308C: lb    $t3, 8($t4)
...
0x801330B8: addu  $v0, $a2, $a1        ; a2 = 缓冲区指针
0x801330C0: lbu   $a0, 8($v0)          ; 比较 buf[8..15]
0x801330C4: lbu   $v0, ($v1)
0x801330CC: beq   $a0, $v0, ...        ; 逐字节比对
0x801330D4: sb    $zero, 6($a3)        ; 不匹配 → 清标志
```

**结论**：游戏校验 `buf + 8` 处的 8 字节是否为 `"MATH_TBL"`，与我们的格式分析一致。

### 3.2 段表遍历

```asm
0x8013311C: lw    $v0, 0x4ca8($v0)      ; 载入 EMI 基址
0x80133124: addiu $a0, $v0, 0x20
0x80133128: lw    $v0, -0x10($a0)       ; 读 size (基址 + 0x10)
0x8013312C: addiu $a0, $a0, 0x10        ; 步长 16 字节
0x80133134: addiu $v0, $v0, 0x7ff
0x80133138: srl   $v0, $v0, 0xb         ; (size + 2047) / 2048 = 扇区数
0x8013313C: addu  $v1, $v1, $v0         ; 累加
```

**结论**：
- 段表位于 `buf + 0x10`，**每项 16 字节**（与我们的解析一致）
- 游戏按 2048 字节扇区计算每个段的 CD 读取长度（流式读取）

## 7. sig 字段的处理方式

对 EXE 全文搜索，字库/图形段的 sig 值
（`0x1C000200` / `0x1E000200` / `0x1A000200` / `0x0A000200`）
**均未以常量形式出现**。

同时：
- sig 高位置位的值（`0x8002E000` / `0x80016000` / `0x8001A800`）是合法的
  PS1 主内存地址（`0x80000000` ~ `0x801FFFFF`）
- sig 最高位未置位的值（`0x1C000200` 等）不对应任何 PS1 硬件地址

**推论**：游戏对段的处理是"通用"的——
高位置位 → 复制到 RAM 地址；否则 → 走另一条路径（图形/字库上传）。
具体分发逻辑仍需在段加载函数中进一步确认。

## 8. 字库加载路径结论

综合静态分析与模拟器实测：

```
开机
  └─ 读取 SYSTEM/INIT.EMI (文件表索引 82)
       └─ 上传 seg7 (sig=0x1C000200, 28672B) → VRAM
            └─ 全局字库就绪 (槽 0-329 全局 + 330-369 场景位)

进入场景 (如 WORLD/AREAD000.EMI)
  └─ 读取该场景 EMI
       └─ 上传其字库段 (28672/30720/32768B) → VRAM (覆盖)
            └─ 槽 0-329: 全局字库副本
               槽 330+:   本场景专属字

打开系统界面 (菜单/商店/存档)
  └─ 这些 EMI 没有字库段 → 沿用当前 VRAM 中已加载的字库
```

**核心结论**：
1. **INIT.EMI seg7 是唯一的全局字库源**（所有系统界面共用）
2. **每个 WORLD 场景 EMI 自带字库段**，进入场景时上传并**覆盖**全局字库
3. 系统界面（无字库段）沿用当前场景已加载的字库
4. 因此汉化必须**同时改写 INIT seg7 与全部 296 个场景字库段**，
   且每个场景段内需包含：槽 0-329 的全局中文字库副本 + 槽 330+ 的场景字

## 9. 对现有汉化方案的两处修正

### 9.1 场景字库起点：349 → 330

```python

```

### 9.2 小字库（0x15 编码）位置仍未定位

编码规则中 `0x15 XX` → 小字库索引 `XX+224`，直接字节 `B` → 小字库索引 `B-32`。

**在 EMI 的全部 297 个字库段中，均未发现小字库（半角/8×8）字形的存放位置。**

若小字库未被子表覆盖，则所有用小字库编码的字符都会显示原版日文字形
——这可能是此前汉化版"部分字符显示异常"的原因之一。

**下一步**：定位小字库字形资源（候选：`INIT.EMI` 的 seg0/seg2，或
`sig=0x1E000200`/`0x1A000200` 图形段中的半角字符区）。
