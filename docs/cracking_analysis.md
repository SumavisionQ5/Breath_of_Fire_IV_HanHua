## 3. EMI 文件格式

### 3.1 头部 (16 字节)

```
偏移   大小   字段         说明
0x00   2      seg_count    段数量
0x02   2      version      版本号
0x04   4      (保留)
0x08   8      magic        "MATH_TBL" 标识
```

### 3.2 段表

从偏移 `0x10` 开始，每段 16 字节：

```
偏移   大小   字段    说明
0x00   4      size    段数据大小 (字节)
0x04   4      sig     段标识 (含 VRAM 加载地址)
0x08   8      (保留)  原始数据 (含加载参数)
```

段数据从偏移 `0x800` 开始，每段按 2048 字节对齐。

### 3.3 段标识 (sig) 含义

sig 的高 16 位为 VRAM/RAM 目标地址的高 16 位：

| sig 值 | 含义 | 目标区域 |
|--------|------|----------|
| 0x1C000200 | 字库数据 | VRAM 0x1C000200 |
| 0x1E000200 | 图形/CLUT | VRAM 0x1E000200 |
| 0x1A000200 | 图形数据 | VRAM 0x1A000200 |
| 0x0A000200 | 图形数据 | VRAM 0x0A000200 |
| 0x80016000 | 文本段 | RAM 0x80016000 |
| 0x8001A800 | 文本段 | RAM 0x8001A800 |
| 0x00000002 | 其他数据 | - |
| 0x00000003 | 其他数据 | - |

### 3.4 INIT.EMI 段结构

```
seg0  sig=1E000200  size=32768   (图形/CLUT)
seg1  sig=8002E000  size=512     (CLUT)
seg2  sig=1A000200  size=32768   (图形数据)
seg3  sig=8002E200  size=512     (CLUT)
seg4  sig=80031E00  size=512     (CLUT)
seg5  sig=80016000  size=1063    (文本段, 256 指针, 30 非空)
seg6  sig=8001A800  size=5964    (文本段)
seg7  sig=1C000200  size=28672   (字库段, 370 glyph 容量)
```

## 4. 文本段格式

### 4.1 结构

```
[指针表] [文本数据]
```

- **指针表**: 开头 u16 `ptsize` 为指针表字节数，后跟 `ptsize/2` 个 u16 指针
- **指针**: 单调递增，指向段内文本数据的偏移
- **文本数据**: 编码后的字节序列，每条以 0x00 结尾

### 4.2 文本检测条件

1. `ptsize >= 16` 且为偶数
2. 指针值单调递增
3. 最后一个指针 ≥ `段大小 - 16`
4. 文本区含 ≥ 3 个 0x12 字节

### 4.3 字符串终止符处理

0x12/0x13/0x15 后跟一个参数字节，不能误判为终止符。提取时使用 `trim()` 函数跳过转义参数。

## 6. 字库/字模格式

### 6.1 字库段概况

全游戏共 297 个字库段 (sig=0x1C000200)，分布在 297 个 EMI 文件中。

| 段大小 | glyph 容量 (21 列) | 场景专属槽 (330+) | 段数量 |
|--------|-------------------|-------------------|--------|
| 28672 (0x7000) | 378 | 48 | 210 |
| 30720 (0x7800) | 388 | 58 | 31 |
| 32768 (0x8000) | 441 | 111 | 56 |

> 容量由 `bof4lib.glyph_capacity()` 按 21 列布局精确计算：
> 段字节数 ÷ 64 = 段行数 → ÷2 (双块并排) = VRAM 行数 → ÷12 取整 ×21 = 容量。
> 28672B = 14 块 → 224 行 → 378 槽；30720B = 15 块 → 第 8 层仅左块 → 388 槽；32768B = 16 块 → 256 行 → 441 槽。

> **历史修正**：早期文档记为「370 / 400 / 420 槽、场景槽 349+」，那是基于已废弃的
> 「64B/行 × 10 glyph 带」布局推算的错误值。现已按 21 列布局重算，并修正全局/场景分界为 **330**。

7 个系统 EMI (CAMP/SHOP/MASTER/MSHOP/SGAMEN/SGAMENX/COMMU03) **无字库段**，直接使用 INIT.EMI 的全局字库。

### 6.2 像素布局 (已通过 VRAM 转储逐字节比对 + 字形渲染验证)

**修正要点**：字库是 **21 列网格**，早期文档描述的「64B/行 × 10 glyph 带」是错的。

```
VRAM 中字库区宽 256 px = 21 列 × 12 px (每列 6 字节, 21×6 = 126 字节)
glyph i 的格位:
  col = i % 21          (0-20)
  row = i // 21
  VRAM 坐标 = (col × 12 像素, row × 12 行)
```

段文件 → VRAM 的映射（关键）：

```
段文件每 2048 字节块 → VRAM 中占 32 行 × 64 字节
相邻两块并排: 左块字节列 0-63, 右块字节列 64-127

VRAM(row, col_byte) → 段内偏移:
  blk     = 2 × (row // 32) + (1 if col_byte >= 64 else 0)
  seg_row = blk × 32 + (row % 32)
  offset  = seg_row × 64 + (col_byte % 64)
```

> 由于 21 × 6 = 126 ≠ 128 (双块宽度)，**部分 glyph 会跨越块边界**
> （如 glyph 10 占字节列 60-65，横跨左块尾部与右块开头）。因此实现必须
> **逐字节**按上述公式取写，不能按整行切片搬运。见 `bof4lib._vram_to_seg()`。

验证方法（本次交叉核对）：
1. 从 `INIT.EMI` seg7 按 21 列布局提取 glyph → 与 VRAM 转储直读**逐字节比对**
2. 结果: 378 槽中 **373 槽完全一致**（余 5 槽为 349-353，游戏运行时已被场景字覆盖，反证 330+ 为场景专属槽）
3. 渲染验证: glyph 0-20 为「中大砂嵐泥流回復天光海特異点最防御変身銃王」，与 `main_font_index.csv` 索引 0-20 完全吻合
4. 单元测试: 跨块 glyph (10/20/21) 与邻居互不覆盖，round-trip 全部通过

### 6.3 4bpp 像素格式

每行 6 字节 = 12 个 4bit 像素：
```
字节排列: [b0, b1, b2, b3, b4, b5]
像素排列:
  像素0 = b0 >> 4 (高 nibble, 左侧)
  像素1 = b0 & 0xF (低 nibble, 右侧)
  像素2 = b1 >> 4
  像素3 = b1 & 0xF
  ...以此类推
```

## 7. 写盘流程

### 7.1 文本段写入

1. 解析 EMI 段表，定位文本段 (is_text_segment 检测)
2. 用 `trim()` 逻辑遍历原始字符串
3. 将编码文本按顺序映射到非空原始字符串位置 (顺序匹配, 非按 ID)
4. 构建新段数据 (指针表 + 编码文本)
5. 如果新段 ≤ 原段大小 (含对齐)，直接写入
6. 如果新段 > 原段，使用 EMI relocation (rebuild_emi)

### 7.2 字库段写入

1. 按 sig == 0x1C000200 定位字库段 (不用 seg index)
2. 清空字库段数据
3. 按 21 列布局逐字写入字模 (`set_glyph`，内部经 `_vram_to_seg` 换算段内偏移)
4. 场景字库段: 写入 349 主字副本 + 场景字 (段大小由 `glyph_seg_size()` 计算)
5. INIT.EMI: 主字库 + 自身场景字合并写入

### 7.3 EMI relocation

当文本段或字库段需要扩容时:
1. 用 `rebuild_emi()` 重建 EMI (段表 + 数据, 保留非替换段)
2. 如果新 EMI 大小 ≤ 原 LBA 空间: 原地写入
3. 否则: 搬移到镜像尾部空闲区 (38.7MB 可用)
4. 更新 ISO9660 目录记录 (LBA + size, LE + BE)

### 7.4 扇区对齐

BIN 镜像中每个扇区 2352 字节 (24 头 + 2048 数据 + 280 ECC)。
写入时必须按扇区对齐：

```python
for i in range(sectors):
    off = lba * 2352 + 24 + i * 2048  # 扇区偏移
    modified[off:off + 2048] = data[i*2048:(i+1)*2048]
```

### 10.1 字库加载路径 (已于 2026-09-17 确认)

**结论**：`INIT.EMI seg7` 只在开机时上传，**不参与游戏内文本渲染**；游戏内文本用的是**当前场景 EMI 的字库段**。

```
开机
  └─ SYSTEM/INIT.EMI → seg7 上传 VRAM (全局字库)

进入场景 (WORLD/*.EMI)
  └─ 该场景字库段上传 VRAM ← 覆盖
       ├─ 槽 0-329 : 全局共享区
       └─ 槽 330+  : 本场景专属字

对话 / 命名 / 菜单（系统文件无字库段）
  └─ 沿用 VRAM 中当前字库
```

**决定性实验**：
- 297 个字库段**全部槽位**填方块 → 游戏内文本绝大部分变方块 ⇒ **文本字体确实来自这些段**
- 仅 `INIT.EMI seg7` 填竖条纹 → 游戏内**完全无变化** ⇒ **INIT seg7 不参与游戏内渲染**

**对汉化方案的要求**：中文主字库必须写入**每一个场景 EMI 的字库段**（296 个），仅改写 `INIT.EMI seg7` 不会被游戏内文本使用。

> 补充佐证：本次交叉核对发现 `INIT.EMI seg7` 的槽 349-353 与运行时 VRAM 不一致，
> 说明这些槽在游戏中已被场景字覆盖——与「分界 330」的结论一致。

### 10.3 8 个超长文本段

### 10.5 容量瓶颈与路径 E (2026-09-18 新增)

全量重译后唯一字符并集 2,087 >> 全局槽 330, 零搬移不可能 (根因: 假名走小字库 1 字节,

寄存器, 无预光栅化缓存), 详见 `clut_banking_design.md`。

### 10.6 文本渲染链路逆向新发现 (2026-09-18)

静态反汇编 (capstone) 定位:

| 项 | 地址/值 |
|----|---------|
| 控制码跳转表 (33 项) | RAM 0x80130948 |
| 0x05 ({色XX}) 处理器 | 0x801389BC: `andi v0, XX, 0x3f` → `ori s0, v0, 0x3c00` |
| 0x12/0x13 共用处理器 | 0x80138A30 (主字库路径) |
| 文本绘制函数 | 0x80138900 (唯一调用点 0x8014440C) |
| 字形精灵尺寸字 | 0x000C000C (12×12, 3 处) / 0x000C0008 (半宽 8×12) |
| 21 列魔数除法 | $s1 = 0x30C30C31 (0x80138BC8 mult) |
| 字体状态切换 | 0x80138004(1=主字库 / 0=小字库) |
| 调色板表 | EMI CLUT 段 (sig=0x800xxxxx, 512B=16 窗口) → RAM 0x8002E000 → VRAM 条带 |
| INIT seg1 内容 | 16 窗口文本调色板 (win0=灰白默认, win1-7=红/绿/蓝/黄等彩色) |

要点:
1. 字形为逐字 12×12 纹理精灵直接绘制, **无预光栅化缓存** → CLUT 分页方案兼容
2. 每基元 CLUT 位置来自寄存器 $s0 (运行时变量), `{色XX}` 原生切换 64 窗口
   → **逐字调色板切换无需给渲染器打补丁**
3. 调色板窗口内容由 EMI 的 CLUT 段决定 = 汉化侧完全可控
4. 状态转储文件的 VRAM 基址非 0x320000 (字库模式实测于文件偏移 0x299E45/55);
   且两个现存状态疑似旧补丁构建下抓取, 后续实验须用原版镜像重抓

详见 `clut_banking_design.md`。
